# Platform capability matrix

Verified 2026-08-29 against the current official documentation linked below. Machine-readable host and model records require revalidation after 2026-11-29. Claude Code and OpenAI Codex are the only supported hosts.

| Capability | Claude Code | Codex (CLI / IDE / app) | Repository decision |
| --- | --- | --- | --- |
| Persistent instructions | Applicable ancestor `CLAUDE.md` and `CLAUDE.local.md` files load at launch; descendant files load on demand when work enters those directories. Discovered files concatenate rather than override. Fewer than 200 lines is guidance, not a hard limit. | Codex loads one instruction file per directory from project root to working directory; `AGENTS.override.md` wins within a directory, and selected files concatenate root to leaf. `project_doc_max_bytes` defaults to 32 KiB for the project chain. | Install one managed project-root block per selected host and no generated nested roots. |
| Always-on and scoped rules | Unscoped `.claude/rules/*.md` files load persistently; `paths:` rules load for matching work. | Persistent guidance belongs in the `AGENTS.md` chain. Stack detail can remain in explicit references or genuine consumer-owned nested instructions. | Load one compact kernel and profile. Thin selected routes point to full references; fresh installs select no stack context. |
| Skills | Project skills live at `.claude/skills/<name>/SKILL.md`; descriptions support discovery and bodies load on use. Frontmatter supports invocation controls, forked execution, custom agents, and tool restrictions. Forks do not inherit conversation history. Claude also provides native `/security-review` and `/verify`. | Repository skills live at `.agents/skills/<name>/SKILL.md`; Codex first exposes name, description, and path and loads the body when selected. Catalog budget is 2% of model context, or 8,000 characters when context is unknown. | Ship ten canonical project skills and no aliases. `aer-security-review` and `aer-verify` avoid replacing native names. Claude review skills use a foreground `Read`/`Grep`/`Glob`-only reviewer; Codex read-only behavior still depends on host permissions. |
| Subagents | Project agents live under `.claude/agents/`; official guidance documents bounded concurrency/depth controls and SDK spend limits. | Codex supports native roles and parallel delegation. | Claude receives one read-only reviewer. Shared guidance requires bounded, scoped delegation; consumer caps remain authoritative. |
| Deterministic policy | Permissions, hooks, managed settings, repository gates, and CI enforce their own scopes. Prompt prose is not a guarantee. | Approval policy and sandboxing are enforcement controls. Experimental command rules govern commands requested outside the sandbox. `PreToolUse` hooks can block or rewrite covered local calls but are not a complete enforcement boundary. Managed requirements, repository gates, and CI enforce their own scopes. | Policy maps remain repository-only research. Installation never overwrites settings or claims to activate enforcement. |
| Model-specific behavior | Official Opus 5 guidance warns that generic final-verification and verifier-subagent prompts can cause redundant work and recommends bounded delegation and explicit scope. | Official GPT-5.6 guidance recommends lean, non-repeated instructions and representative evaluation. | Model records guide corpus design and evaluation only. Static distributions remain model-neutral and inject zero overlay prompt bytes. |
| Plugins | Claude plugins package skills, hooks, agents, MCP, and related components, but a plugin-root `CLAUDE.md` is not project instruction context. | Codex supports repository marketplace discovery, but installs plugins into a user cache/config and does not support plugins in the IDE extension. | Repository marketplaces do not supply the cross-host root composition, profile/context selection, collision handling, and ownership contract required here. The `aer` project installer is canonical; global npm packaging only makes its executable available. A skills-only plugin may be a future optional channel. |
| Installation and updates | Projects can already contain instructions, settings, rules, skills, and agents. | Projects can already contain `AGENTS.md`, skills, and nested instruction chains. | `aer init` is greenfield and refuses unowned collisions. `update`, `doctor`, and `uninstall` use portable file/root-block hashes and root-boundary provenance from a repository ledger. All AER-managed state remains project-local; no global agent state is required or written. |
| Load validation | Roots, always-on rules, matched context routes, the selected profile/skill, and reviewer prompts have different load timing. | Root-to-working-directory concatenation, byte caps, and absolute skill paths make aggregate and target-specific checks necessary. | Simulate 36 canonical installed-marker-aware plans with exact active-profile, skill, model-record, duplicate-ID, conflict, and host-cap closure. The 3,500-token estimator excludes references read later and consumer/host context. |
