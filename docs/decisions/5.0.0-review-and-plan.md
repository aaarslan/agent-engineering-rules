# AER 5.0: review, decision, and implementation plan

Status: implemented and locally verified on 2026-09-12; [verification record](5.0.0-verification.md). This plan starts from released v3.1.1 (`c1353c7`), on `feature/AER0005`. The rejected v4 branch, `feature/AER0004` at `af7803f`, remains unchanged and is not an ancestor of v5. No publication or paid evaluation is authorized by this work.

## Product requirements

The user's grievances are requirements and design evidence, not a claim that a benchmark has measured them. V5 must deliver complete, coherent engineering with economical execution. Completeness determines the required outcome; simplicity determines its implementation. Diff size is neutral, including evidence-based subsystem redesign and replacement. Neither a symptom patch nor speculative architecture satisfies this target.

The requirement inventory is [grievances.json](../../source/evals/grievances.json). It preserves every supplied grievance ID, assigns an owning rule or repository policy, and distinguishes design coverage from measured efficacy. The map is checked locally; a valid map does not prove model adherence.

The historical artifacts remain retrievable from those revisions; they are not rewritten into a favorable comparison.

The committed Codex roots measured 183 physical lines / 10,360 UTF-8 bytes in v2, 79 / 7,356 in v3.1.1, and 74 / 7,238 in v4 with hook conditionals rendered off. These counts describe the root, not total prompt cost. V4's mandatory verification reference adds substantial reading that its runtime budgets omit. These measurements are not adherence or performance evidence.

V2 supplies the clear engineering target, but its long always-on load and ban on broad rewrites should not return. V3 supplies the stable project-local installer, compact IDs, stronger universal obligations, and concern-specific references. V4 supplies useful failure evidence and some isolated packaging lessons; its control runtime is rejected.

## Implementation

1. **Kernel and corpus.** Preserve the stable directive identities, restore high-stakes engineering obligations, add normative strength and a visible execution order, and give completion its own objective predicate. Enforce the complete kernel below the user's physical-line ceiling and within the byte budget. Audit profiles, task skills, design, review, UI, and verification references for contradictions, hidden mandatory reads, rewrite aversion, duplicate authority, and testing ceremony. Repository frameworks, visual systems, and tool choices remain repository-owned.
2. **Installation and diagnostics.** Retain v3 ownership, collision, boundary, interrupted-update, and uninstall protections. Extract the shared manifest from the builder. Keep useful existing diagnostics behind one optional `aer verify` entrypoint with explicit check selection and honest applicability/error outcomes. Do not auto-detect or execute project scripts. Ship runtime files once at the package root and copy only the selected payload into the project. Add no hook, daemon, service, model adapter, report gate, or session state.
3. **Research validation.** Replace dormant evaluation execution with provider-free validation of live directive/scenario closure, grievance ownership, frozen treatment integrity, policy/compatibility records, and actual load budgets. Keep historical treatment/fixture bytes intact. Preserve negative tests that protect these contracts; do not measure efficacy with phrase matches.
4. **Documentation and release.** Mark v4 as unreleased and superseded, version v5 directly from v3, document migration and the removed runtime assumptions, record the grievance map and evaluation limitations, and verify current platform claims from official documentation. V5 makes no efficacy claim.
5. **Integration and review.** Rebuild distributions, inspect the installed variants and package inventory, exercise the optional diagnostic and installation lifecycle, run the required repository tests and validators once at the integration gate, and repair/recheck only affected failures. Inspect tracked and untracked changes, generated identity, consumer safety, dead paths, and all material limitations before reporting completion.

## Delegation and ownership

The orchestrator owns this decision, grievance traceability, release/evaluation documentation, compatibility evidence, combined verification, and final review. Astra with high effort owns corpus changes requiring engineering judgment. Sol with high effort owns the bounded packaging/installer/diagnostic work and the separate provider-free validation work. Agents receive disjoint file ownership; they do not run paid evaluations, publish, or recursively delegate. Their results are inspected, not automatically accepted or rerun wholesale.

## Acceptance criteria

- V5 branches directly from v3.1.1; v4 is preserved, not merged or released.
- Every supplied grievance has a real owner; no assertion equates coverage with proven behavioral improvement.
- The entire kernel has stable IDs, explicit normative strength, authority, optimization target, execution order, completion conditions, and enforced physical-line/byte budgets.
- Proposed mechanisms do not silently become constraints; sufficient engineering evidence can justify a larger replacement.
- Exact behavior, real integration, protected reads and writes, persistent data, lifecycle, recovery, and final repository coherence remain explicit obligations.
- Disposable projects prioritize a complete working path; durable regression investment depends on stable behavior, exposure, risk, and failure cost. Existing production regressions and repository gates still matter.
- No unconditional verifier, broad-suite cadence, report grammar, command ledger, or mandatory diagnostic scan survives in installed guidance.
- Baselines, frozen research inputs, historical failures, and authorization limits remain honest and inspectable. Validation and CI require no provider credentials or calls.
- Generated distributions match source; the packed install and upgrade preserve consumer-owned content and expose no repository-only research payload.

## Deliberate departures

- V4's runtime and its profile mechanisms are not carried forward: their cost and false guarantees conflict with the motivating requirements. V5 assurance profiles describe evidence investment, not hook machinery.
- V4's completion report schema is removed: evidence content matters; exact punctuation does not establish correctness.
- Historical measurements, versions, IDs, and frozen experimental values remain in their historical records. They are evidence, not configurable operational thresholds; current tunable budgets have one source configuration owner.
- No live comparison is run during product repair. Structural validation can establish installation and corpus consistency, not model efficacy; a future evaluation requires a separately approved protocol and spend.
