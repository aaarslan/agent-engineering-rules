# AER v7 rearchitecture study

Status: study only, prepared 2026-10-05 from the `main` tree at `1815475`
(v6.0.0). Nothing in this document changes the published package, the
installed payload, or any efficacy claim. It records what the codebase is,
what is wrong with it, what a better architecture looks like, whether that
architecture is feasible, and which decisions only the maintainer can make.

Platform statements below were checked on 2026-10-05 against the current
official Claude Code documentation (`code.claude.com/docs`) and OpenAI Codex
documentation (`developers.openai.com/codex`). They are dated here and are not
yet reflected in [the capability matrix](../capability-matrix.md).

## 1. Verdict in one paragraph

The product is about 130 KB of authored prose: a 5.4 KB contract, three
profiles, thirteen short skill bodies, twenty-four reference documents and
three diagnostic scripts. Everything else in the repository exists to copy,
own, verify, freeze, or trace that prose, and it now outweighs the product by
roughly twenty to one in files and bytes. The installer solves a transaction
problem that git already solves for every consumer; the research corpus
re-implements content addressing that git already provides; the evaluation
layer has been "prepared" through four major versions without ever running;
and the delivery model defaults to a file Claude Code ignores in any repository
that has a `CLAUDE.md`. A rearchitecture is feasible and worthwhile. It should
shrink the repository to the content plus a thin, idempotent renderer, deliver
through each client's native mechanism instead of a shared managed block, and
replace frozen-but-unexecuted evaluation design with a small evaluation that
actually runs.

Derived measurements, all taken on this checkout:

- The composed always-on block is 6,709 to 6,818 bytes and 57 lines depending
  on profile. The skill catalog adds up to 3,602 characters on Codex. The
  repository estimates that at roughly 2,600 tokens before any task content.
- One destination installs 188 files and 424 KB into the consumer repository.
  The default Codex plus Claude Code pairing installs about 850 KB, of which 24
  documents are unique. Every reference is copied into every skill whose link
  closure reaches it, so `security.md` (which links `web-ui.md`) drags the
  entire web stack into `aer-securing-code` and `aer-building-backend-apis`.
- All thirteen evaluation fixtures contain a byte-identical `app.mjs`,
  `index.html` and `baseline.test.mjs`; the 39 case prompts differ by one
  opening sentence. The 140 routing cases are five positive and five negative
  one-line prompts per skill. Offline validation proves that this template
  machinery is internally consistent and nothing else.
- The main test suite passes 34 of 36 on Node 22.22; the two failures are the
  CLI's own engine gate (`requires Node >=24.11.1`), not a defect. Every
  validator (`validate-v6`, `validate-runtime-loads`, `validate-corpus`,
  `validate-evals`, `validate-links`) passes.
- Version history: 13 commits, 24,622 insertions in the v6 commit alone, four
  incompatible delivery architectures (1.0 router, 2.0 dual dist, 3.0 CLI with
  rules, 5.0 managed block plus contexts, 6.0 standalone skills plus ledger).
  No release has carried an efficacy measurement for the delivery it shipped.

## 3. Findings

Findings are grouped by layer. Each names the evidence in this checkout and the
consequence for a consumer or maintainer. Severity is my judgment of how much
the item limits adoption or maintainability, not a defect count.

### 3.1 Delivery model

**F1. The default instruction file is one Claude Code does not read in most real repositories.** `selection()` in `src/payload.mjs` defaults `instructionsFile` to `AGENTS.md`. Claude Code documentation states that `AGENTS.md` is read only when no `CLAUDE.md`, `.claude/CLAUDE.md` or `CLAUDE.local.md` exists in the working directory or above (default setting `claude-md-or-agents-md`, v2.1.277+). Any repository that already uses Claude Code has a `CLAUDE.md`, so the contract is silently absent. `check` only prints an advisory note afterwards. The v6 execution record accepted this as an "explicitly reviewed `@AGENTS.md` bridge". A consumer should not need to know that. Severity: high.

**F2. A shared managed block inside a consumer-owned file is the most expensive ownership shape and the only client that needs it is Codex.** The block logic in `src/block.mjs`, the ownership record (`createdFile`, `separator`, `tail`), BOM and CRLF preservation, block moves between files and the "unowned managed block" refusals exist because AER writes into a file it does not own. Claude Code offers a file AER could own outright: `.claude/rules/<name>.md` loads at startup with no `paths`, and loads on demand with `paths`. Owning a whole file turns the block problem into a plain file-hash problem that the rest of the installer already handles. Codex has no equivalent (it concatenates `AGENTS.override.md`, `AGENTS.md`, then `project_doc_fallback_filenames` per directory, up to `project_doc_max_bytes`, 32 KiB default), so the block is justified only there. Severity: high.

**F3. The always-on UI clause taxes every repository for a defect observed once in a todo app.** `kernel/block.md` includes `{{ui}}` unconditionally; [the delivery decision](5.0.0-ui-interaction-delivery.md) traces this to one unblinded low-effort GPT-6 Astra comparison. Claude Code `.claude/rules/*.md` with `paths: ["**/*.{tsx,jsx,html,css,vue,svelte}"]` delivers exactly this clause only when UI files are touched. On Codex the clause can live in the web skill alone. Severity: medium.

**F4. Thirteen near-synonymous skill names compete for implicit routing.** Claude Code loads every non-manual skill's description on every turn (capped at 1,536 characters each). Codex lists all thirteen at root and nested cwd. `aer-implementing-features`, `aer-designing-code`, `aer-refactoring-code` and `aer-securing-code` all plausibly match an ordinary feature prompt, and the repository's own routing cases mark three of them as "supporting" for each other. Nothing measures how often the wrong one fires. Descriptions also carry meta text ("Explicit invocation only on integrated clients") that the client already enforces mechanically through `disable-model-invocation` and `allow_implicit_invocation: false`; on Claude Code that text is not even shown for manual skills, because manual skills' descriptions are not loaded. Severity: medium.

**F5. Reference duplication is caused by link closure, not by the standalone requirement.** `tools/content-manifest.json` lists, per skill, the transitive closure of markdown links from its SKILL.md. Because `security.md` links `web-ui.md`, `web-ui.md` links `typescript-react.md` and `ui-styling.md`, and `principles.md` links `performance.md`, almost every skill ends up with 12 to 18 references it never names. Cutting the cross-links (mentioning a sibling document by name without a link) would reduce copies to the 1 to 3 references each SKILL.md actually lists, roughly an 80% reduction, with no change to the standalone guarantee. Severity: medium, cheap to fix.

**F6. The repository is not usable as a skills source by the generic installers the ecosystem has standardized on.** `npx skills add <owner>/<repo>` (skills.sh, Vercel) installs any directory containing `SKILL.md` into Claude Code, Codex, Cursor, Copilot, Gemini CLI and 40 other agents. AER's skills are already Agent Skills spec-compliant (the `parseSkill` validator enforces the spec's name and description limits), so the repository could be installed that way today, except that nothing documents it and the kernel is not reachable by that path. A bespoke installer competes with a free, maintained one. Severity: medium for adoption.

**F7. Plugins were deferred on a premise that no longer holds.** The v2.1 matrix recorded that plugins cannot deliver rules files, which is still true for `CLAUDE.md` and `.claude/rules/`. But plugins can deliver skills, agents, hooks and output styles, and an output style with `force-for-plugin: true` and `keep-coding-instructions: true` appends the plugin's instructions to the system prompt while keeping Claude Code's built-in engineering instructions. That is a documented always-on delivery path for the contract on Claude Code that needs no managed block, no ledger and no hook. Its caveat is that it overrides the user's chosen output style. Severity: medium; this changes the delivery options table.

### 3.2 Installer runtime

**F8. The transactional installer protects against a threat model the consumer already covers with git.** `src/install.mjs`, `src/fs-safe.mjs`, `src/state.mjs` and `src/plan.mjs` implement an exclusive run lock with owner identity, a pending-operation journal with before/after hashes and raw byte hashes, per-file atomic temporary-and-rename, post-write snapshot guards comparing BigInt device, inode, nanosecond mtime and link count, orphaned-temporary detection, resume-with-same-request rules, and keep-modified detachment. [The v6 record](6.0.0-plan.md) itself scopes the guarantee to "recoverable process interruption with file sync/rename; not power loss or a hostile filesystem owner". For a tool that writes markdown into a git working tree, the equivalent guarantee is "run it in a clean tree; `git diff` shows exactly what changed; `git checkout` reverts it". The same code also forced the Node 24.11.1 floor (F9). An idempotent installer whose only guard is "never overwrite a file whose current hash is not one AER wrote" needs no journal: after any interruption, rerunning converges, because files already written match the new expected hash and files not yet written match the old one. The `resuming` branch in `plan.mjs` already accepts either hash; the journal only decides which branch runs. Severity: high for maintainability.

**F9. The Node floor is an artifact of F8, and it excludes Node 22 LTS for no content reason.** The 24.11.1 minimum exists because Node 24.0.0's libuv reported inconsistent `st_dev` on Windows and the snapshot guard compares device identity exactly. Everything except the engine gate runs on Node 22 here. The floor is a real adoption cost (CI images, corporate baselines) bought to support a guard that F8 argues should not exist. Severity: medium.

**F10. The runtime is written in a style the product's own contract forbids.** Most of `src/` is 150 to 300 character lines with multiple statements per line, single-letter bindings and chained ternaries (for example `expectedFiles` and `mutate`). `source/shared/principles.md` says "optimize for the reader". Reviewers of this installer, including the maintainer in six months, pay the cost. This is cheap to fix once the code shrinks. Severity: low alone, high combined with F8.

**F11. Package-supplied deletion authority grows without bound.** `integrations/payload-history.json` must carry, for every prior v6 release, the hash of every rendered file for every representation plus three block hashes, so that a newer package can uninstall or upgrade an older install. It is empty today because 6.0.0 is the first v6. By 6.5.0 it will be the largest file in the package and every release must regenerate it correctly or lock consumers out of upgrade. A simpler contract is "the ledger records the hashes AER wrote; AER removes any owned path whose current hash equals its ledger hash", which is what `check` already verifies and needs no package history. Severity: medium, latent.

**F12. The three-command CLI is tested well but its surface is wider than its users.** `--destination representation:PATH` repeated, `--instructions-file`, `--profile`, `--skills`, `--keep-modified`, five exit codes and eleven JSON statuses model every combination the installer can reach. The README's own quick start uses two destinations and defaults. The exercised recovery commands in `INSTALL.md` (stale lock inspection, journal temporaries, pending kinds, unowned remnants) are documentation for failure modes that a simpler installer cannot enter. Severity: low; falls out of F8.

### 3.3 Content

**F13. The kernel is written for a validator, not for a model.** The contract packs 26 directives into 5.4 KB using slash-joined lists ("owner/behavior/surface/risks/checks"), bare MUST clauses, and no examples. The repository's own `AGENTS.md` says "add rules only for observed or reproducible failures; remove rules that do not change behavior", but no directive has ever been ablated, so the set is the union of every grievance ever filed (110 of them, all "efficacy: unmeasured"). Anthropic's published prompting guidance for the Claude 4 family favors fewer, specific instructions with the reason stated, and warns that over-constrained prompts produce rigid behavior; practitioners report the same per-rule adherence decay as rule counts grow. The byte budget treats the kernel as a token cost problem; after the first turn it is mostly a cached prefix, so the real cost is attention, not dollars. Severity: high, because this is the product.

**F14. Repository-level assurance profiles are a weak lever.** Profiles differ by 70 to 110 bytes of guidance and are chosen once per repository at install time. Assurance actually varies per task: a throwaway spike happens in a production repository and a payments change happens in a prototype. The model can read the task; the profile mostly restates `AE-21` and `AE-25`. Severity: low; simplification opportunity.

**F15. Every skill carries the safety fragment twice.** The `aer:shared-safety` fragment is inlined into each SKILL.md and the same text is copied again as `references/contract.md` (310 bytes, named like the kernel contract but unrelated to it). The name collision between `kernel/contract.md` and `references/contract.md` is a maintenance trap. Severity: low.

**F16. The review subagent cannot see the diff it is asked to review.** `integrations/claude-code.json` restricts `aer-code-reviewer` to `Read, Grep, Glob`. The skill body therefore requires the caller to paste base, head, changed paths and the complete diff into the packet, and tells the fork to "report the omission" otherwise. Claude Code subagent `tools` accept permission patterns; a read-only `Bash(git diff:*)`, `Bash(git log:*)`, `Bash(git show:*)` allowance would let the reviewer gather its own scope while remaining unable to write. This should be verified against the current permission syntax before relying on it, but the documented shape exists. Severity: medium for the two manual review skills' usability.

**F17. Model-specific overlays exist as dormant data.** `research/compatibility/models.json` describes "overlays" for Claude Opus 5 and GPT-6 Astra with behavior flags that are never rendered anywhere, while `AE-24` mandates model neutrality. Either the overlays are a design the product wants, in which case they belong in `integrations/` and the renderer, or they are not, in which case the validator that checks their review dates is maintenance with no consumer. Severity: low.

### 3.4 Quality apparatus and research

**F18. Frozen history re-implements git.** `research/evals/frozen-history.json` pins 37 files by SHA-256 and `validate-corpus.mjs` hashes them on every run and additionally pins the manifest's own digest. Git already content-addresses every file at `c1353c7993b4ff78e09963b01207d8b2d2c5d29e`; `git show <rev>:<path>` is immutable and needs no validator. The semantic map (`before`/`after` text of every directive) and source map (where every v5 file moved) are one-time migration records validated forever. Severity: medium for maintainer time, zero for consumers.

**F19. The v5 package is vendored in full to test the exit path.** `test/fixtures/v5` (234 files, 1.9 MB, 9,300 lines of retired tooling) is copied to a temp directory and its 77 tests run on every release check in every CI cell, and `packed-install-smoke.mjs` packs it to exercise `aer@5.0.0 uninstall`. The same immutability is available from a single pinned tarball (`aaarslan-aer-5.0.0.tgz`, integrity-checked) committed as one binary fixture, which also tests the artifact consumers actually received rather than a source copy. The current AGENTS.md policy ("preserve the immutable v5 fixture and its regression assertions") forbids this; it is a maintainer decision, see §6. Severity: medium.

**F20. Validators enforce the shape of research, not the truth of the product.** `grievanceErrors` requires exactly IDs 1 through 110, each owned by a live directive, each "unmeasured". `compatibilityErrors` fails the build when a review date passes (`revalidate_after`), which forces a maintainer to bump a date rather than re-verify. The CI matrix (two Linux, two Windows, one research) runs the full release check including the v5 suite and a real npm pack and install on each cell, about 20 minutes per cell for a package with zero runtime dependencies. Severity: medium.

### 3.5 Evaluation

**F21. Four major versions of evaluation design, zero executed runs under the design.** The repository contains an evaluation policy, a four-arm study index, a protocol template, a record validator, rubric, holdout policy, 39 cases and 13 fixtures, and the phrase "no efficacy claim" appears in nearly every document. The only observations are two informal todo-app comparisons with an unblinded evaluator and one observation per arm. The policy's prohibition on provider dispatch in CI is sound; its effect in practice has been that nobody dispatches anywhere. For a product whose entire value is changed model behavior, this is the central risk: the maintainer cannot tell whether v6 is better than v5, v3, or nothing. Severity: critical.

**F22. The prepared fixtures cannot discriminate.** One toy module, one 12-line HTML file, and one sentence of task per case cannot exercise `AE-14` lifecycle, `AE-15` data changes, or `AE-16` external contracts. A credible evaluation needs ten to twenty real tasks in real repositories with hidden tests, even if small. Severity: high.

### 3.6 Documentation and positioning

**F23. The public documents are written for an auditor, not an adopter.** README sentences such as "A floating version does not preserve treatment bytes" and "Isolated client-control probes do not establish model efficacy" lead the page. A new reader cannot find what AER does to their agent's behavior, what one skill looks like, or why they would want the contract. The honesty is valuable; the ordering is not. Severity: medium for adoption.

## 5. Proposed architecture

### 5.1 Principles

1. The content is the product. The repository's committed tree is the
   installable artifact; nothing is generated and committed.
2. One wording authority per document, and references are linked by name
   from skill bodies, not from each other.
3. Deliver through each client's native mechanism. A shared managed block is
   the fallback, used only where the client has nothing better.
4. The installer is a pure function from (package, selection) to a file set,
   applied idempotently; git is the consumer's transaction log.
5. Every rule earns its place by an observed failure and keeps it by an
   evaluation that can be rerun. Rules without an eval case are candidates
   for removal.
6. Validation checks the product (spec compliance, links, budgets, rendering
   determinism). History lives in git, not in validators.

### 5.2 Repository layout

```
contract/                   # always-on text, one file per client-neutral unit
  contract.md               # the engineering contract (rewritten, see 5.4)
  assurance.md              # one proportional-evidence paragraph (replaces profiles)
  web-ui.md                 # UI-01 clause, path-scoped on Claude Code
skills/<name>/SKILL.md      # 8 to 9 skills, spec-compliant, installable as-is
skills/<name>/references/   # only the references the body names; symlink-free copies produced at pack time
skills/<name>/scripts/      # unchanged diagnostics
references/                 # the 24 shared documents, single copy
agents/aer-code-reviewer.md # Claude Code reviewer, read-only plus git read commands
plugin/                     # Claude Code plugin manifest, output style, marketplace entry
src/aer.mjs                 # ~200-line installer: render, apply, check, remove
tools/validate.mjs          # spec, links, budgets, pack determinism
evals/                      # runnable paired evaluation, outside CI (see 5.6)
docs/                       # adopter-first README, capability matrix, decisions
```

Rendering (copying each named reference into its skill, adding Codex sidecars
and Claude frontmatter) happens in `prepack` and in `aer install`, never into
the committed tree. `npm run validate` renders to a temporary directory and
checks determinism and link closure there. The `payload-manifest.json`
inventory becomes the rendered output's manifest, generated at pack time.

### 5.3 Delivery per client

| Client | Always-on contract | UI clause | Skills | Reviewer | Manual-only control |
|---|---|---|---|---|---|
| Claude Code, project files | `.claude/rules/aer-contract.md` (owned whole file) | `.claude/rules/aer-web-ui.md` with `paths` | `.claude/skills/<name>/` | `.claude/agents/aer-code-reviewer.md` | `disable-model-invocation: true` plus `context: fork`, `agent` |
| Claude Code, plugin | Output style (`force-for-plugin`, `keep-coding-instructions`) or documented one-line `@` import | Same output style, or rules file installed by the project path | Plugin `skills/` | Plugin `agents/` | Same frontmatter |
| Codex | Managed block in `AGENTS.md` (only remaining block case) | In the web skill body only | `.agents/skills/<name>/` plus `agents/openai.yaml` | Not applicable | `allow_implicit_invocation: false` |
| Any other agent | Documented paste for its instruction file | In the web skill body | `npx skills add aaarslan/agent-engineering-rules` | Not applicable | Description text only |

The Claude Code path no longer touches `CLAUDE.md` or `AGENTS.md` at all. If
the maintainer prefers the contract inside `CLAUDE.md`, the installer prints
the one import line to add; it does not edit the file.

### 5.4 Content changes

- Rewrite the contract as roughly ten to twelve rules in plain sentences with
  the reason stated, keeping the `AE-nn` identifiers for traceability in a
  mapping table rather than in the text. Target under 3 KB. Put one concrete
  example on each of the three rules with the highest observed failure rate
  (`AE-20` status, `AE-13` invalidity, `AE-26` completion). Everything else in
  the current 26 becomes a reference sentence or is dropped pending an eval
  case (principle 5).
- Replace three profiles with one paragraph in the contract ("scale evidence
  by lifespan, exposure and failure cost; disposable work still needs a working
  path") and let the user say "prototype" or "high assurance" in the task.
  Keep a `--assurance` install option only if the eval shows the paragraph is
  insufficient.
- Merge skills to eight or nine: `implementing` (absorbs designing-code's
  checkpoint and the securing-code obligations as a reference), `fixing`,
  `refactoring`, `changing-data`, `building-web-ui`, `building-backend-apis`,
  `writing-docs`, `reviewing-changes` (manual), `reviewing-security` (manual),
  `running-long-tasks` (manual). `verifying-work` becomes a reference loaded by
  `reviewing-changes` and by the contract's completion rule, since its body is
  mostly a restatement of `AE-18` through `AE-21`.
- Make descriptions pure trigger text: what the skill does, when to use it,
  what it is not for. Remove enforcement meta text.
- Remove the inlined safety fragment from skill bodies on clients that load
  the contract, keep it only in the portable rendering (the renderer already
  knows the client).
- Remove reference-to-reference links; references mention siblings by name.

### 5.5 Installer specification

`aer` keeps three verbs with a smaller contract:

- `aer install [--target DIR] [--client claude-code|codex|portable]... [--skills LIST] [--dry-run] [--json]`
  renders the selection, refuses if the target is not a git repository with a
  clean status for the paths it would touch (overridable with `--force-dirty`),
  writes files that are absent or whose current hash equals a hash in
  `aer.lock.json`, refuses on any other collision, and writes the ledger last.
  Rerunning after an interruption converges because every path is either
  untouched, already at the new hash, or at the old recorded hash.
- `aer check` compares the ledger to the tree and reports drift. Unchanged.
- `aer uninstall [--keep-modified]` removes owned paths whose hash matches
  the ledger, removes the Codex block only if its hash matches, and reports
  the rest. No journal, no run lock, no pending state, no payload history.

Removed from the runtime: run lock and owner identity, pending journal and
temporaries, BigInt device and inode guards, Windows device normalization,
orphan temporary detection, the `uniqueJson` duplicate-key scanner,
`payload-history.json`, five of the eleven output statuses. The engine floor
drops to `>=22`. Target: about 200 readable lines plus about 150 lines of
tests, replacing 701 dense lines plus about 450.

What is lost: protection against a second AER process mutating the same tree
at the same instant, and recovery guarantees for an interruption between
writing the Codex block and writing the ledger (the rerun will see an unowned
block and refuse; the user resolves it with `git checkout AGENTS.md`). The v6
record already excludes power loss and hostile processes; the remaining window
is milliseconds in a tree the user controls.

### 5.6 Evaluation that runs

- Ten to twenty real tasks drawn from small public repositories with hidden
  tests and one or two seeded cross-cutting defects each, covering the
  failure classes the contract claims to fix (status honesty, invalid input,
  lifecycle, consumer updates, completion claims). The existing templated
  fixtures are retired.
- A paired design per client: baseline (no AER), contract only, contract plus
  skills. Three repetitions per cell, blinded grading by a rubric with a
  hidden test pass as the strict score and a short human quality review.
- A runner script in `evals/` that the maintainer invokes locally with an
  explicit budget cap; it never runs in CI and never reads credentials from
  the repository. The study-record validator is kept as the record format.
- The first run's purpose is to rank rules by effect, which is the input to
  principle 5. The second run, after trimming, is the efficacy baseline for
  v7. Budget order of magnitude: tens of dollars per cell with current
  pricing for a 15-task, 3-repetition design on a mid-tier model; the
  maintainer authorizes the actual figure.

### 5.7 Validation and CI

`npm run validate` becomes one script: frontmatter spec compliance, reference
link closure within each rendered skill, contract byte budget, rendered-output
determinism (render twice, compare), link check in docs, personal-path check.
`npm test` covers the installer against a temporary git repository: install,
idempotence, drift refusal, interrupted-rerun convergence, uninstall, Codex
block insert and remove, Claude rules files. The v5 exit test consumes a
single pinned `aaarslan-aer-5.0.0.tgz` fixture. CI runs one Linux and one
Windows cell on Node 22 and Node 24; total wall time target under five
minutes per cell.

Retired: `research/` as a validated corpus (the files move to
`docs/history/` with a README pointing at their source revisions, or are
deleted in favor of `git show`), `validate-corpus.mjs`, `validate-evals.mjs`,
`validate-runtime-loads.mjs` (its one useful number, the always-on byte count,
moves into `validate.mjs`), `test-legacy.mjs`, the `research-preflight` CI
job, and the expiry-dated compatibility registries (the capability matrix
keeps the dated claims as prose).

## 6. Feasibility

### 6.1 Effort

Estimates assume one maintainer working with an agent, in focused days.

| Phase | Work | Days | Risk |
|---|---|---:|---|
| A. Content | Rewrite contract, fold profiles, merge skills, strip meta text, de-link references, new README | 4 to 6 | Medium: wording changes behavior; needs the eval in D to confirm |
| B. Delivery | Claude rules files, path-scoped UI clause, plugin manifest and output style, Codex block kept, generic-installer layout, reviewer tool allowance | 3 to 4 | Low to medium: plugin and output-style behavior must be probed on the real client as in v6 |
| C. Runtime | New 200-line installer, tests, drop journal and lock, Node 22 floor, pinned v5 tarball fixture | 3 to 4 | Low: the new code is simpler than the tests it replaces |
| D. Evaluation | Task set, runner, first paired run, rule ranking, second run | 5 to 8 plus budget | High on outcome, low on execution; this is the first real evidence the project will have |
| E. Repository cleanup | Move or delete research and vendored v5, single validator, CI | 2 | Low |
| F. Migration and release | 6.0.0 to 7.0.0 path, changelog, decisions, capability matrix refresh | 2 | Medium: 6.0.0 consumers need a documented exit |

Total: roughly three to five weeks of focused effort, with phase D the
only one whose result is uncertain.

### 6.2 What is preserved

- Every `AE-nn` identifier, in a mapping table, so decision records and
  grievance history remain readable.
- Spec-compliant skills with self-contained rendered directories; the
  standalone property is unchanged.
- Read-only preview, hash-owned installation, drift refusal, consumer byte
  preservation outside owned paths.
- Explicit manual invocation and the restricted reviewer on Claude Code,
  implicit-invocation exclusion on Codex.
- No telemetry, no automatic hooks that enforce anything, no provider calls
  in CI, no mandatory verifier or report grammar.
- The historical bytes of every prior release, through git.

### 6.3 What changes for 6.0.0 consumers

A 6.0.0 install is removed with `aer@6.0.0 uninstall` (its own tested path)
before installing 7.0.0, exactly as v6 required for v5. Alternatively the v7
installer reads a v6 ledger and removes owned paths whose hashes match, since
the ledger format already records every hash; this is a few dozen lines and
avoids a two-package dance. The `AGENTS.md` block is removed for Claude-only
consumers and replaced by `.claude/rules/aer-contract.md`; Codex consumers keep
a block with new marker names.

### 6.4 Policy conflicts that need the maintainer's decision

The current `AGENTS.md` contributor rules forbid several steps above. Each
needs an explicit yes or no; the study does not assume either.

1. "Preserve the immutable v5 fixture and its regression assertions; no v6
   cleanup adopts v5 ownership." Replacing the vendored tree with a pinned
   tarball keeps immutability and drops the 77-test suite from every CI run.
2. "Do not add hooks/mods." A plugin output style is not a hook, but a
   `SessionStart` hook that injects the contract would be, and it is the only
   plugin path that does not override the user's output style. The study
   recommends the output style and documents the hook as rejected.
3. "Enforce the complete kernel's physical-line and byte budgets" and the
   `kernel/thresholds.json` ownership rule. The rewritten contract keeps a byte
   budget; most other thresholds disappear with the code they parameterize.
4. "CI must never receive provider credentials or execute live evaluation
   adapters." Unchanged. The study adds a maintainer-run evaluation outside
   CI, which the current policy already contemplates but never scheduled.
5. "A behavior-expanding rule change requires a paired live evaluation."
   Phase A is a behavior change in both directions; phase D is that
   evaluation. Shipping A without D would repeat the pattern of every prior
   major version.
6. The Node floor and the transactional guarantees in `INSTALL.md` are
   public promises of 6.x; dropping them is a major-version change and should
   be stated as such in the changelog.

### 6.5 Risks and mitigations

- **Client drift.** Claude Code changed skill and memory semantics several
  times in 2026. Mitigation: the delivery layer is per-client data plus a
  thin renderer, probed on the real client before each release as v6 did, and
  the capability matrix is refreshed with dates.
- **Routing regressions from merging skills.** Mitigation: the routing cases
  become part of the phase D run (observe which skill fires), not an offline
  contract.
- **Losing the honesty culture while simplifying docs.** Mitigation: keep
  the "what this does not prove" section, move it below the adopter content.
- **Over-correction on the installer.** Mitigation: keep collision refusal,
  owned-hash deletion and dry-run; those are the guards consumers actually
  rely on. Drop only the machinery that exists for sub-second races.

## 7. Phased plan

1. Phase C first (installer and layout), because it unblocks everything and
   its risk is lowest; release as 7.0.0-alpha with unchanged content so the
   delivery change is isolated.
2. Phase B (native delivery), probed on Claude Code and Codex with the
   loopback method recorded in `docs/evidence/6.0.0-client-controls.json`.
3. Phase D first run on the unchanged content, to obtain the first baseline
   and the per-rule ranking.
4. Phase A (content rewrite) guided by that ranking; phase D second run.
5. Phases E and F; release 7.0.0 with the first efficacy table the project
   has published, including its uncertainty.

## 8. Open questions for the maintainer

- Is Codex still a first-class target, or is Claude Code the primary
  consumer? The answer decides whether the managed block survives at all.
- Is a Claude Code plugin marketplace entry wanted? It is the lowest-friction
  path for Claude users and the only one that needs no file in the consumer
  repository.
- What evaluation budget and which models are authorized for phase D? The
  existing policy names ZAI, DeepSeek and Meta as intended providers; the
  consumers of AER are Claude Code and Codex, so the evaluation should run on
  the models those clients actually use.
- Should the 110-grievance inventory remain a living requirement list or
  become a historical record? The study assumes historical, with the eval
